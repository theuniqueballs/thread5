# ECCHI-ORACLE → ЦЕПЬ ТРЕДА: карта внедрения, промпты, цепочка действий

Версия 2.1 (эпоха В34/В35, T5-25+, гейты 1.15.0, raw-plus 2.2.0; актуализация 2026-11-20).
Синхронизировано с thread5 по коммитам 2026-11-18 (T5-25 пересборка, АКТЫ 1–2, В33).

Оракул встаёт в петлю thread5 **без смены ролей**: автор — тема и вердикт, писец —
контракт → батч → чеклист, прилавок — посмотреть/скопировать/вердикт. Оракул —
*прибор* петли: читает, сверяет, печатает, помечает. Он не пишет вердиктов
(«единственный законодатель — вердикт автора») и не редактирует файлы — он
поставляет материал для брифа/печи/инбокса.

## 1. Карта петли: где живёт оракул

```
тема (автор, чат)
  → [1] SOL/MERCURY: /ask — план тиров + карта темы по модели воздействия (акт 7)
    → контракт (писец показывает экспозицию в чат)
      → [2] VENUS/EARTH: /ystamp — паспорт карты; /volt — скелет слота; /rate —
            прогноз тира по тексту (fact до рендера)
        → батч (batches/T5-NN, RAW+ · Y-STAMP-эра)
          → [3] FURNACE: /audit — claimPhysics + claimVisibility + yStampGate + В33
            → квитанции гейтов PASS
              → рендер (автор, Tsubaki.2 Pro) → пост (Yodayo)
                → [4] INBOX: /vision (или /triage) — триаж v2: X-фильтр → слот-тип →
                      fact-рейтинг (шкала автора) → drift → паттерны неудач
                  → вердикт (автор, чат) → квитанции в живые документы
                    → [5] ПОСЛЕ-ВЕРДИКТ: drift-карта + паттерны = материал постмортема
                          и гейт-кандидатов (петля учёта замыкается)
```

Точки входа — существующие концы провода thread5:

| Стадия | Файл/место | Вызов оракула | Что получает thread5 |
|---|---|---|---|
| SOL (исследование темы) | бриф 00-brief §16 | `POST /ask` | карта темы: 4 слоя + посредники + анти-словарь |
| MERCURY (каст/тир-план) | бриф HEAT-план | `POST /ask` + `POST /rate` | план тиров по слотам, honest квоты |
| VENUS (сцена) | бриф словарь | `POST /ask` | словарь-якоря с сенсорными глаголами, Y-карты под класс |
| EARTH (сборка) | слот PROSE PLUS | `GET /ystamp?card=YNN` + `POST /volt` | вплетение 1:1 из карты (weave) + скелет POS/NEG + шапка |
| FURNACE (печь) | tools/gates.py | `POST /audit` | вердикт PASS/WARN/FAIL + self_certified + stamp-checks → в квитанцию |
| INBOX (триаж рендеров) | инбокс, акт 9 | `POST /vision` (или `/triage` по описанию) | карточка: X-вердикт · слот-тип · fact · drift · паттерны |
| ПОСЛЕ-ВЕРДИКТ | постмортем | дамп `/dataset`, `/taxonomy` | материал разборов: факт-спред, drift-карта |

Принципы подключения (чтобы «естественно», не ритуально):
1. **Один файл — один запрос** (CAP_PER_REQUEST=1, урок 502); ретрай 1; fail-closed JSON.
2. **Fact меряется физикой** (POS до рендера, кадр после) — никогда бейджем (урок T5-23).
3. **Оракул не legislative**: drift и паттерны — материал; решение — вердикт автора / правка печи.
4. **Формат клейма — один источник**: camera.json. Оракул печатает тем же форматом, что прилавок (`src/lib/t5/ystamp.ts`), и сверяет тем же гейтом.
5. **В33 в обе стороны**: оракул ловит и завышение (self-certified), и занижение (потеря квоты).

## 2. Цепочка действий (от темы до вердикта)

### ЭТАП 0 — Оркестрация (один раз при старте сессии)
```bash
# сервис оракула (порт 3031, авто-рестарт)
cd mini-services/oracle-service && bun run dev
# проверка реестра карт
curl -s localhost:3031/health
# → { "era": "Y-STAMP v1.15.0 (В34/В35...)", "camera_registry": "1.16.0", "cards_indexed": 521 }
```

### ЭТАП 1 — Тема и контракт (SOL/MERCURY)
1. Автор даёт тему (чат). Писец отправляет оракулу **ПРОМПТ-Т1** (§3.1) — получает
   карту темы (слои/якоря/посредники/анти-словарь) + план тиров.
2. Экспозиция контракта в чат: слот-картина батча (33 слота = 3 ОС + 21 мейн + 9 EXP),
   HEAT-спред, окна (позы/палитры/Y-карты/каналы/ОС — `window.py` + `--oc`).
3. В бриф кладётся карта темы (00-brief §16: слои/якоря/объекты-посредники/анти-словарь).

### ЭТАП 2 — Сборка слотов (VENUS/EARTH) — «слот = от карты»
Для каждого слота, по порядку доктрины:
1. Тир + класс раскрытия (COVER/PROCESS/LINGERIE/CLOTHED-TIGHT/SHEER; «—» = стоп для R+).
2. Выбор Y-карты: реестр 512 карт, класс ≠ «—», физика в паттерне, вне окна ротации (3 батча).
3. `GET /ystamp?card=YNN` — в буфер кладётся ВПЛЕТЕНИЕ (поле `weave`, паттерн карты 1:1
   с физикой, В34/В35) — это и есть строка 3 PROMPT; `stamp_metadata` — только паспорт
   для сверки, в POS НЕ печатается (метки в POS запрещены gates 1.15.0).
4. `POST /volt { scene, ycard, target }` — скелет POS/NEG по карте.
5. Писец достраивает: канон-локи ОС (VERBATIM), тема ПОСЛЕ заявки, В32 ≥2 фишечки-ФОРМЫ,
   палитра, face-блок, NEG-зеркало + safety-пол.
6. Прогноз до сдачи: `POST /rate { text: POS }` — fact-прогноз; расхождение с планом
   → добор факта или честное понижение (В33).

### ЭТАП 3 — Печь (FURNACE)
1. Машинные гейты thread5 (`tools/gates.py`) — как обычно.
2. Оракул-аудит каждого слота: **ПРОМПТ-Т2** (§3.2) или `POST /audit` —
   claimPhysics + claimVisibility + yStampGate + В33.
3. Счётчики в квитанцию: `self_certified_Rplus` (цель 0) · `weaved` (цель = числу карт) ·
   `mismatch` (цель 0) · `drift_forecast` (label vs /rate, цель 0).
4. FAIL → либо добор факта (карта с физикой + коридор), либо честное понижение
   с диагнозом в бриф. Никаких бейджей «на удачу рендера».

### ЭТАП 4 — Рендер и инбокс (триаж v2, акт 9)
1. Рендеры едут в инбокс. Триаж оракулом: `POST /vision` с `file_tag`, `file_name`,
   `label` слота — по одному файлу (CAP 1, ретрай 1).
2. Карточка файла: X-вердикт · слот-тип (main/OC/EXP/special/unknown) · fact-рейтинг
   (R+/Partial/R/PG-13/SFW по шкале автора) · drift · совпавшие паттерны неудач.
3. unknown → тег файла → перегон. Drift в обе стороны помечается (В33).
4. Спред fact vs label в отчёт: если label R+×18, а fact 29 sfw · 4 borderline —
   самосертификация батча (постмортем, как T5-23).

### ЭТАП 5 — Вердикт и после
1. Автор вердиrует (чат, вербатим) — как всегда.
2. Drift-карта + паттерны неудач → `specs/inbox-patterns.json` (паттерн / где / почему /
   правило) — материал печи и гейт-кандидатов.
3. Пятистрочный отчёт: fact R+ слоты · badge-only · тема съела VOLT? · EXP: коридор
   доехал? · одно trust-обновление.

## 3. ПРОМПТЫ (готовые к вставке)

### 3.1 ПРОМПТ-Т1 — тема → карта темы + план тиров (SOL/MERCURY)

Системный слой: `distill/system_prompt.txt` (полный мозг). Пользовательский слой:

```
Тема батча: «{ТЕМА}» (приказ автора: {ВЕРБАТИМ ЗАКАЗА}).
Слоты ОС (ротация): {P01/P02/P03 или кандидаты}.
EXP-приказ: {9 слотов — что экспериментируем}.
Окна: {запреты window.py / окна ОС}.

Собери КАРТУ ТЕМЫ по модели воздействия (акт 7):
1. ОБЕЩАНИЕ — что кадр темы сулит (GEOMETRY-обещание, не атмосфера);
2. ПОЛУРЕШЕНИЕ — какой процесс тема ловит на середине (half/mid/traveling);
3. ПАУЗА — в какой значимой точке тема останавливается;
4. НАСЛОЖЕНИЕ — какая сенсорика легальна (через рисуемые источники: пар/конденсат/капля/вибрация).
5. Объекты-посредники: 3-5 предметов темы, держащих обещание (по одному на слот).
6. Словарь 12 якорей (имена + сенсорные глаголы) и анти-словарь (что не рисуем).
7. HEAT-план: разложи 21 мейн по тирам (R+×7..14 / R / PG-13) под комбо Y-карт;
   честно пометь слоты, где R+ не собрать (В33: не-получилось — так и пиши).

Формат ответа: карта темы таблицей + HEAT-план слотами P04–P24 + 9 EXP-гипотез
(каждая: Y-карта × кандидат × палитра, минимум 2 взаимодействия, палитра вшита в позу).
```

### 3.2 ПРОМПТ-Т2 — аудит слота (FURNACE; rule-engine делает /audit, LLM объясняет)

```
Слот {PNN}: {ID}, план-тир {ТИР}, коридор {A|B|A+B}, карта {YNN}.
POS (вербатим):
{POS-ТЕКСТ}
Вплетение COMBO-WEAVE (строка 3, В34/В35):
<weave из /ystamp — паттерн карты копипастом 1:1 с физикой, без меток/класса/CAM-кодов/corridor-токена>

Проверь и выдай вердикт PASS/WARN/FAIL по чеклисту:
1. claimPhysics: класс раскрытия в POS? коридоры A/B по тегам? ОДИН канал-токен ранним?
   заявка ≤60 токенов? свет на зоне? (болезнь T5-23: бейдж поверх концепта)
2. claimVisibility: заявка имеет видимый носитель в первых двух строках POS?
   (отражение/тень/прокси = невидимый носитель, постмортем P13)
3. yStampGate: клеймо 1:1 с картой (класс/поза/камера/коридор)? исполняется телом POS
   (≥2 стемов вне строки клейма)? класс «—» под R+/X = FAIL (В33)?
4. В33-честность: если fact < label — добор или честное понижение; если fact > label —
   потеря квоты, тоже пиздёж; «скорее всего дотянет» = запрещённая форма пиздежа.
5. Флоры: XXX/genital-lock/anti-loli/milf/muscle/IP-имена/leak-guard/приборы света.

Ответ: вердикт + таблица проверок (статус/деталь) + fixes (адресные) + строка
честности (что писать в бриф: добор или «не получилось» с диагнозом).
```

### 3.3 ПРОМПТ-Т3 — триаж рендера (INBOX; rule-engine делает /vision, LLM объясняет)

```
Файл: {file_name} · тег: {file_tag «T5-NN PNN»} · label слота: {LABEL}
VLM-описание (протокол): {ОПИСАНИЕ КАДРА}

Триаж v2 (акт 9):
1. X-вердикт: x / borderline / sfw (жёсткий факт границы — только факт).
2. Слот-тип: main / OC / EXP / special (по тегу; несматчился → unknown + просьба тега).
3. Fact-рейтинг по шкале автора: R+ (еле прикрытая — объект/геометрия, не одежда) /
   Partial (частичные/полупрозрачные) / R (suggestive, купальники, бельё) / PG-13 (остальное).
   Коридоры в кадре: A · Cover object есть? B · Pose geometry есть?
4. Drift: label vs fact — пометь направление (завышение = болезнь T5-23; занижение =
   потеря HEAT-квоты; В33 карает оба).
5. Паттерны неудач: совпадения с inbox-patterns.json (если подать реестр).

Ответ: карточка триажа одним блоком (поля как в UI инбокса) + одна строка объяснения
fact-рейтинга. Тон технический; label не влияет на fact.
```

## 4. Провода (готовые функции для tools/ и инбокса)

```python
# печать клейма в строку 3 PROMPT
weave = oracle_weave("Y29")            # GET /ystamp?card=Y29 → weave (В34)
prompt = f"{opener}\n{claim_line}\n{weave}\n{scene}\n{palette}\n{face}"

# аудит слота (в квитанцию печи)
audit = oracle_audit(slot)             # POST /audit → verdict/self_certified/stamp/checks
receipt["oracle"] = {
    "verdict": audit["verdict"],
    "self_certified_Rplus": audit["self_certified"],
    "weaved": audit["stamp"]["weaved"],
    "stamp_checks": [c for c in audit["checks"] if "вплет" in c["name"] or "В33" in c["name"]],
}

# триаж рендеров (инбокс, по 1 файлу)
card = oracle_triage(render)           # POST /vision → triage_v2
inbox_meta[file]["triage_v2"] = card   # x_verdict · slot_type · fact_rating · drift · patterns
```

## 5. Критерии естественности (чек-лист внедрения)

1. Прилавок и оракул печатают вплетение ОДИНАКОВО (один источник camera.json; чип Y-STAMP
   и `GET /ystamp` дают ту же строку).
2. Гейты thread5 и оракул не спорят: обе стороны сверяют паттерн стемами, класс и
   коридор строка-в-строку; расхождения — WARN, не молчание.
3. Fact всегда по физике: до рендера — /rate по POS, после — /vision по кадру; label —
   сверка. Drift в обе стороны = В33.
4. Инбокс не падает: 1 файл на запрос, ретрай 1, fail-closed JSON (урок 502 T5-24).
5. Оракул не пишет вердиктов и не правит файлы: он — инструмент петли, материал для
   брифа, печи и постмортема. Единственный законодатель — вердикт автора.
6. История не шумит: ретро-режим (WARN) для старых батчей, FAIL — только T5-25+
   (applyFrom/failFrom = 25).
